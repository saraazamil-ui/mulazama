# MULAZAMA — Encrypted Backup Report (Phase 05-B)

## النطاق والقرار

تمت مراجعة وتنفيذ واختبار وحدة C12 في `src/persistence/backup.ts` باستخدام Web Crypto الفعلي في Node.js. نجحت اختبارات الملف المشفر والتحقق السلبي وحد الاستبدال في المخزن المرجعي. **لا يكفي ذلك لاعتماد النسخ والاستعادة إنتاجيًا**: معاملات IndexedDB الفعلية، واجهة اختيار الملفات، وانقطاع العملية داخل المتصفح أو أنظمة الهاتف لم تتحقق في هذه البيئة.

## الصيغة المنفذة

| العنصر | التنفيذ الفعلي |
|---|---|
| معرّف الصيغة | `MULAZAMA-ENCRYPTED-BACKUP` |
| إصدار الصيغة | `1`؛ تُرفض الإصدارات والخوارزميات غير المدعومة |
| التشفير والمصادقة | AES-256-GCM، وسم 128 بت، وIV عشوائي 12 بايت لكل تصدير |
| اشتقاق المفتاح | PBKDF2-SHA256، عدد دورات ثابت 600000، وsalt عشوائي 16 بايت |
| كلمة الاستعادة | 12 نقطة Unicode على الأقل، حتى 1024 بايت UTF-8؛ تُرفض سلاسل UTF-16 غير السليمة بدل تحويلها بصمت إلى U+FFFD |
| البيانات المصادق عليها | حقول الرأس المحددة كاملة بصيغة canonical بوصفها AAD؛ تُرفض الحقول الإضافية |
| محتويات الحمولة | `snapshot` و`payloadHash` فقط؛ SHA-256 لتمثيل السجل canonical داخل الحمولة المصادق عليها |
| السجل | حفظ معرفات الأحداث والتوقيتات والإصدارات؛ قبول مطابق دقيق لـVERSIONS أو LEARNING_VERSIONS فقط، ورفض معرف الحدث المكرر والإصدارات غير المدعومة والبيانات غير القابلة للتمثيل كـJSON سليمة |
| الحدود | ملف حتى 32 MiB، حتى 100000 حدث؛ حد تصدير الحمولة أكثر تحفظًا لمراعاة زيادة Base64 والرأس |
| الاستعادة | فحص الملف وفك المصادقة ثم التحقق من إعادة التشغيل قبل `EventStore.replace`؛ استبدال كامل بعد تأكيد صريح وCAS، دون دمج |

تستخدم العملية مفتاحًا مشتقًا غير قابل للاستخراج عبر Web Crypto. لا تصدّر الوحدة مفتاح الجهاز المحلي. لا تتضمن هذه الحزمة تسجيلًا صوتيًا. وجود `payloadHash` فحص إضافي للحمولة، وليس بديلًا عن مصادقة GCM.

## العيوب التي أعيد إنتاجها وأصلحت

| العيب | أثره | الإصلاح والاختبار |
|---|---|---|
| قبول Date وMap في بيانات الحدث قبل canonical | تمثيل غير أمين للبيانات؛ تحولهما دالة canonical إلى كائن فارغ | استخدام `validateEvent` المشترك قبل التصدير أو قبول الحمولة؛ BK05B01 بحالتي Date وMap |
| دورة مرجعية داخل بيانات الحدث | RangeError بدل رفض مدخل مضبوط | التحقق من JSON قبل canonical؛ BK05B03 |
| قبول حقول ملف إضافية خارج AAD | قبول بيانات وصفية غير مصادق عليها مع ملف صالح؛ لم تكن تُستخدم لفتح جلسات أو اعتماد محتوى | حصر حقول الصيغة 1 ورفض المجهول؛ BK05B04 |
| قبول حقول snapshot إضافية تُسقط عند الاستبدال | ادعاء قبول نسخة لا تُستعاد جميع حقولها | مخطط snapshot محدد؛ BK05B05 |
| خيارات استعادة غير موجودة | TypeError غير مصنف، دون كتابة بيانات | رفض INVALID_INPUT قبل حد الاستبدال؛ BK05B06 |
| قبول UTF-16 غير سليم في كلمة الاستعادة | تطابق بايتات أسرار نصية مختلفة بعد تعويض surrogate غير سليم | رفض السلسلة غير القابلة لذهاب وإياب UTF-8؛ BK05B07 |
| قبول شكل حمولة إضافي داخل ملف مصادق عليه | غموض مخطط الصيغة 1 | حصر `snapshot,payloadHash`؛ BK05B10 |

تختبر BK05B02 أيضًا رفض undefined والدوال والأعداد غير المنتهية. وتختبر BK05B08 عد نقاط Unicode. وتُنشئ BK05B09 حمولة UTF-8 غير سليمة مصادقًا عليها بمفتاح اختبار معلوم؛ ومن ثم فإن سبب رفضها هو محلل المحتوى، وليس مجرد فشل وسم التشفير.

## الاختبارات المنفذة وحدود الدليل

البيئة: macOS، Node.js 24.22.1، Vitest 3.2.4، Web Crypto في Node. تستخدم اختبارات ذرية الاستبدال `MemoryEventStore` المعلن بوصفه مخزنًا مرجعيًا فقط.

الأمر:

```sh
PATH=/tmp/mulazama-baseline/bin:$PATH node node_modules/vitest/vitest.mjs run src/persistence/backup.test.ts src/persistence/backup05b.test.ts --reporter=verbose
```

- الاختبارات السابقة B01–B13: 13 اختبارًا ناجحًا.
- الاختبارات الجديدة BK05B01–BK05B10: 11 حالة ناجحة، لأن BK05B01 يختبر Date وMap منفصلين.
- المجموع: **24 ناجحًا، صفر فاشل، صفر متجاوز** في التشغيل المستهدف بعد الإصلاح. سجل التشغيل: `docs/05b/evidence/backup-regression-after.txt`.
- قبل الإصلاح أظهر التشغيل الأول للاختبارات الجديدة 8 إخفاقات و3 حالات ناجحة. لم يُحفظ stdout لهذا التشغيل في ملف؛ لا يوجد ملف دليل سابق مختلق.
- احتُفظ أيضًا بسجل تكاملي وسيط فعلي: `docs/05b/evidence/backup-integration-intermediate.txt`، وفيه 23 حالة ناجحة وواحدة فاشلة بسبب مرجع VERSIONS أثناء تغيير واجهة طبقة التعلم. أصلح مالك الطبقة المرجع وأصبحت التهيئة تستخدم صلاحية اختبار صناعية محددة؛ أُعيد التشغيل فنجحت الحالات الأربع والعشرون، دون حذف assertions.

نجح فحص TypeScript مبكرًا قبل تغيير واجهة صلاحيات التعلم. يتحقق الفحص العام النهائي في تقرير التسليم؛ لا يُستبدل به تشغيل الاختبارات أعلاه ولا يُستنتج نجاحه من تحويل Vitest للمصدر.

تشمل الأدلة السابقة والحالية: كلمة سر خاطئة، تغيير ciphertext، تغيير الرأس، ملف مبتور، إصدار/KDF غير مدعوم، معرف مكرر، إصدار محرك/محتوى غير متاح، غياب التأكيد، استبدال بدل الدمج، استعادة متكررة دون تكرار الأحداث، فشل replay، فشل كتابة مرجعية مع حفظ الأصل، وكتابة متزامنة أثناء الفحص يرفضها CAS. لا تمثل هذه النتائج اختبار SQLite أو IndexedDB أو عملية حفظ ملف على القرص.

## إصلاح عيب إعادة التشغيل

كشف فحص تكاملي مستقل أن `replayLearning` كان يقبل حدثي تكرار لهما معرفا حدث مختلفان ومعرف أمر واحد، ويزيد العداد من 1 إلى 2 بعد تصدير ملف وفحصه باستخدام `replayLearning`. أعيد إنتاج ذلك في `/tmp/mulazama-backup-review-repro.ts` وأُحيل إلى مالك طبقة التطبيق. أصبحت الطبقة ترفض إعادة استخدام أمر HME في حدث مختلف. يثبت BK05B10 الآن تصدير النسخة ذات الأمر المكرر ثم رفض استعادتها باستخدام `replayLearning` الفعلي بـEVENT_CONFLICT، مع بقاء السجل الأصلي والعداد 1. نجح هذا الاختبار في التشغيل النهائي المحفوظ.

يدعم EventStore العام أوامر متعددة الأحداث، ولذلك لم تُفرض سياسة «حدث واحد لكل أمر» عالميًا داخل صيغة النسخة. أُدخل LEARNING_VERSIONS بإصدار `hme-application-evidence-05b.1`؛ يقبل فاحص الملف الغلافين الموثقين بالضبط، وتظل أهلية إعادة تشغيل سجل تعلم تاريخي خاضعة لخدمة التعلم. لا يُعاد تفسير سجل HME 05-A وفق قواعد 05-B بصمت؛ يحتاج هجرة معتمدة صريحة مع حفظ الخام.

## نموذج التهديد والقيود

تحمي الصيغة سرية الملف المنقول وسلامته عند امتلاك ملف مشفر دون كلمة الاستعادة. ترفض المصادقة كلمة الاستعادة الخاطئة والعبث بالبايتات قبل استبدال بيانات المستخدم. لا تمنع محاولة تخمين كلمة استعادة ضعيفة دون اتصال، ولا تحمي من XSS أو شيفرة تعمل تحت أصل التطبيق أو جهاز مخترق أثناء إدخال الكلمة أو عرض البيانات المفكوكة. ليس هذا تدقيقًا خارجيًا مستقلًا للتشفير.

توجد كلمة الاستعادة والنص المفكوك في ذاكرة عملية JavaScript أثناء التشغيل، ولا يوجد ادعاء بمحو مضمون لسلاسل الذاكرة بعد جمعها. تعيد وحدة التصدير سلسلة JSON مشفرة ولا تدعي نجاح حفظها إلى وجهة ملفات. لا تدعي الوحدة حذف ملفات نسخ خارجية أو حذفًا فيزيائيًا آمنًا لملفات مؤقتة؛ ذلك يخضع لمنصة الملفات والمتصفح. لا يوجد ادعاء تحقق من Keychain أو Android Keystore أو تشفير جهاز كامل.

## الأعمال المتبقية قبل الاعتماد

1. تنفيذ اختبارات الاستبدال والفشل المتزامن وإعادة الفتح والترحيل على IndexedDB حقيقي في المتصفحات المدعومة؛ الحالة الحالية **غير متحقق منها**.
2. توسيع إثبات ذرية رفض استعادة الأمر المكرر من المخزن المرجعي إلى IndexedDB الفعلي؛ اختبار HME+C12 المرجعي ناجح ومحفوظ.
3. اختبار واجهة التصدير والفحص والتأكيد والإلغاء وإدارة كلمات الاستعادة والتنزيل والملفات على المتصفح والمنصات المتاحة فعليًا.
4. إقرار سياسة توافق النسخ عند تغير إصدارات المحرك أو المحتوى؛ الرفض الحالي صريح بدل إعادة تفسير سجل قديم بصمت.
5. مراجعة أمنية مستقلة وسياسة حماية/حذف على كل منصة قبل أي ادعاء جاهزية إنتاجية.
