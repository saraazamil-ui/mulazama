# 09-B — حقول إعداد بيئة MULAZAMA وتجربة القبول

هذه تعليمات لتعديل **بيئة التطوير السحابية فقط**. لم تُحفظ هذه الحقول أو تُنشر من مهمة 09-B. الأدوات المتاحة تعرض حالة البيئة، ولا تعرض نص الحقول الحالي أو أحدث مسودة أو زر نشر؛ لذلك أسماء الحقول أدناه وظيفية وقد تختلف ترجمتها في الواجهة. لا تمثل الخطوات وصفًا لواجهة فُحصت فعليًا.

## القيم المطلوب حفظها

| الحقل | القيمة |
| --- | --- |
| البيئة | افتحي إعداد البيئة الحالية `mulazama`، مع الاحتفاظ ببقية إعداداتها |
| المستودع | `https://github.com/saraazamil-ui/mulazama` |
| فرع المصدر | `main`؛ لا تثبتي المهمة على SHA قديم |
| مسار المستودع المعدّ | `/workspace/mulazama` |
| مجلد البدء، إن وجد | `/workspace`؛ مسار العمل الفعلي يُطبع بعد كل تشغيل ناجح |
| Node.js | الإصدار الحالي 24.22.1 يفي بشرط 24+ |
| pnpm | `11.25.0`، مطابق لـ`packageManager` في `main` وقت 09-B |
| Python | Python 3؛ اختُبر 3.12.14 |
| متغير البيئة | `MULAZAMA_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium` |
| برنامج التثبيت / Setup script | الصقي **كامل محتوى** [`scripts/cloud-bootstrap09b.sh`](../../scripts/cloud-bootstrap09b.sh)، من أول سطر إلى آخر سطر، وليس أمرًا يشير إليه داخل المستودع القديم |
| تعليمات بدء التشغيل / Startup instructions | النص التالي كاملًا |

لا يلزم تغيير الأسرار أو الشبكة أو الاستضافة أو النطاق. احتفظي بالقيم القائمة. Chromium الحالي 156.0.8078.79 متاح في المسار المحدد؛ لا تجمعي هذا الاختيار مع `PW_CHANNEL`.

```text
في بداية كل مهمة جديدة لمشروع MULAZAMA، قبل تثبيت الاعتماديات أو تعديل أي ملف:
1. سجّل معرّف البيئة وsource_config_version_id، والوقت، ثم الفرع وHEAD وorigin/main وحالة Git في /workspace/mulazama قبل أي جلب أو إصلاح. لا تعتبر origin/main المحلي دليلًا على أحدث GitHub.
2. نفّذ python3 /workspace/mulazama-cloud09b/bootstrap.py مرة جديدة لهذه المهمة. لا تعتمد على نتيجة تشغيل محفوظة من إعداد الصورة أو مهمة سابقة. إذا كان الملف مفقودًا أو فشل الأمر فتوقف عن التثبيت والتعديل وأبلغ بسبب الفشل؛ لا تستخدم نسخة قديمة بديلة.
3. اقرأ MULAZAMA_WORKTREE وMULAZAMA_BOOTSTRAP_EVIDENCE من خرج هذا التشغيل نفسه. تحقق من result.json: status=ready وinstallSucceeded=true وhead=fetchedMain، ومن الوقت وrunId الخاصين بالمهمة. انتقل إلى MULAZAMA_WORKTREE في جميع الأوامر التالية؛ /workspace/mulazama قد يبقى قديمًا عمدًا لحفظ العمل السابق.
4. سجّل git ls-remote origin refs/heads/main في نسخة العمل الجديدة وقارنه بـHEAD. إذا تغيّر main أثناء البدء، احتفظ بالتشغيل السابق وأعد تشغيل bootstrap في نسخة جديدة قبل العمل. لا تعِد ضبط أي فرع ولا تحذف أي ملف.
5. اقرأ AGENTS.md من النسخة الحديثة. للعمل استخدم فرع codex الجديد الذي أنشأه bootstrap. افتح Draft PR فقط عند الحاجة؛ لا تعدّل main مباشرة ولا تدمج ولا تنشر الموقع.
6. عند طلب التحقق الكامل، نفّذ MULAZAMA_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium python3 scripts/verify-08a.py --output /workspace/mulazama-09b-verification بعد حفظ التغييرات المطلوبة في commit على الفرع المستقل. سجّل النتائج الجديدة والفشل والتجاوز والحجب كلًا على حدة. لا تغيّر القرآن أو مصادره أو FSRS أو Hifz Mastery Engine أو تفسير سجلات المستخدمين، وأبقِ productionReady=false وG01–G10 blocked.
7. افصل في التقرير بين الحالة قبل bootstrap وبعده، وبين تنفيذ الوكيل لتعليمات البدء وتشغيل hook آلي من المنصة. لا تدّع نشر البيئة أو نجاح التشغيل التلقائي دون دليل من مهمة مستقلة تستخدم النسخة المنشورة.
```

برنامج التثبيت مستقل عن محتويات اللقطة القديمة. يحفظ مشغّلًا في `/workspace/mulazama-cloud09b/bootstrap.py` ثم ينفذه. كل تشغيل للمشغّل يجلب `main`، يتحقق من استمرار الأصل المعتمد ومن عدم إعادة كتابة التاريخ المرصود، وينشئ worktree وفرعًا جديدين، ثم يشغّل `cloud-start08a.py --check` من الشفرة المجلبة ويثبت من ملف القفل. لا يبدّل فرع نسخة المصدر ولا يتخلص من تعديلاتها. يبقى المشغّل السابق محفوظًا ويُرفض الاستبدال إذا اختلف محتواه؛ تحديثه لاحقًا يحتاج مسارًا ذا إصدار جديد ومراجعة واضحة، وليس الكتابة فوقه.

**تنبيه وظيفي:** حقل «تعليمات بدء التشغيل» نص يُوجّه الوكيل، وليس بالضرورة hook تنفيذيًا. إن كانت واجهتك توفر أمرًا تنفيذيًا مضمونًا لكل **مهمة جديدة**، ضعي فيه `python3 /workspace/mulazama-cloud09b/bootstrap.py`، واحتفظي بتعليمات اختيار مسار العمل. لا يكفي تشغيل Setup مرة واحدة قبل أخذ snapshot، ولا يوجد دليل هنا على أن hook كهذا متاح. لا تضعي تشغيلًا ينشئ فرعًا جديدًا عند كل استئناف لمهمة جارية؛ يُعاد استخدام مسار عمل المهمة الجارية مع حفظ تعديلاتها.

## الحفظ والنشر من واجهة Codex

1. افتحي إعدادات بيئة `mulazama` المرتبطة بهذا المشروع، ثم راجعي المستودع والفرع والحقول أعلاه. احتفظي بالمستودعات والمتغيرات والإعدادات الأخرى القائمة.
2. الصقي برنامج التثبيت كاملًا وتعليمات البدء، ثم استخدمي **Save draft** إذا كان متاحًا. راقبي سجل الإعداد: يجب أن يظهر `fetch-main` ناجحًا، ومسار worktree جديد ونتيجة تثبيت ناجحة. احتفظي بمعرّف التشغيل ونسخة الإعداد؛ لا تعتبريه دليلًا على بدء مهمة مستقبلية.
3. بعد اكتمال الإعداد ومراجعاته وتوقف محادثة الإعداد، استخدمي **Publish** الخاص **بالبيئة** عندما تتيحه الواجهة. هذا ليس نشرًا للموقع. سجّلي معرّف النسخة المنشورة الجديدة؛ إذا لم يظهر الحفظ أو النشر، فالحفظ الدائم لم يكتمل.
4. افتحي محادثة Codex Cloud جديدة مستقلة وحددي بيئة `mulazama` بالنسخة المنشورة. لا تستأنفي 09-B أو محادثة إعداد البيئة لإجراء اختبار القبول.
5. أرسلي نص القبول التالي. لا تنقلي ملفات من Mac، ولا تشغّلي إصلاحًا يدويًا بين إنشاء المهمة وتسجيل حالتها الأولى.

```text
اختبار قبول مستقل لإعداد MULAZAMA 09-B. سجّل أولًا البيئة وsource_config_version_id والفرع وHEAD وorigin/main وحالة Git والملفات الموجودة قبل أي إصلاح يدوي. بيّن هل نفّذ Setup أو تعليمات البدء فعلًا في هذه المهمة، مع توقيته ومعرّف تشغيله وسجل frozen-install. اسمح لتعليمات البدء المنشورة بالتنفيذ؛ لا تعوّض غيابها بإصلاح يدوي غير معلن. إذا غابت أو فشلت، أبلغ أن القبول فشل وتوقف عن تكرار اختبارات قديمة بوصفها دليلًا.
قارن HEAD في مسار عمل هذه المهمة بأحدث refs/heads/main على GitHub، وشغّل التحقق الكامل من ملف القفل مع Chromium المصرح به. أثبت TypeScript والبناء والاختبارات البرمجية والمتصفح وFSRS وسلامة النسخ والاستعادة، وبقاء productionReady=false وG01–G10 blocked. اذكر الحالة الخام للّقطة منفصلة عن مسار العمل الذي جهزه bootstrap تلقائيًا؛ لا تسم نجاح نسخة مؤقتة دليلًا على حفظ الإعداد. لا تعدل main ولا تدمج ولا تنشر.
```

النجاح الدائم مشروط بدليل تلك المهمة الجديدة. إذا بدأت اللقطة الخام قديمة لكن آلية البدء جهزت تلقائيًا worktree حديثًا قبل العمل، تُذكر الحالتان صراحة؛ لا يُقال إن اللقطة الخام نفسها كانت حديثة.
