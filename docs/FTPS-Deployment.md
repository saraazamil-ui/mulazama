# إعداد نشر مُلازَمَة عبر Explicit FTPS

هذا إعداد للبناء والتحقق والنشر اليدوي إلى `https://mulazama.com`، وليس موافقة على الإطلاق. يعتمد على المشروع الحالي دون إعادة تصميمه أو تغيير FSRS أو التخزين أو مصادر القرآن. يظل `productionReady=false` وتظل G01–G10 محجوبة حتى اكتمال اعتمادها المستقل.

## الاتصال والمسار

- الأسرار الموجودة في GitHub Actions: `FTP_SERVER` (اسم مضيف فقط، دون بروتوكول أو منفذ أو مسار)، و`FTP_USERNAME` و`FTP_PASSWORD`. لا تُنسخ قيمها إلى المستودع أو السجلات أو وسيطات الأوامر.
- البروتوكول **Explicit FTPS**: اتصال على **21** ثم `AUTH TLS` قبل إرسال بيانات الدخول؛ حد أدنى TLS 1.2، مع التحقق من شهادة الخادم واسم المضيف، و`PROT P` لتشفير قناة البيانات السلبية. لا رجوع إلى FTP غير المشفر أو تعطيل للتحقق من الشهادة. ليس SFTP أو Implicit FTPS على 990.
- الوجهة ثابتة **`./`** بالنسبة إلى مجلد الدخول. بناءً على إعداد المالكة للحساب، يمثل هذا المجلد `public_html`. لا تستخدم `public_html/` أو `/public_html/` لأن ذلك قد ينشئ مستوى إضافيًا داخل جذر الحساب.
- الفحص يثبت نجاح `PWD` ثم `CWD ./` وبقاء المجلد نفسه، ونجاح عرض المجلد بقناة بيانات مشفرة. لا يعرض أسماء الملفات. مسار `PWD` افتراضي داخل حساب FTP؛ لا يثبت وحده الربط الفيزيائي بـ`public_html`، الذي يعتمد على إعداد الحساب المذكور من المالكة.
- إن فشل التحقق من الشهادة، استخدم اسم مضيف FTP المطابق للشهادة من شركة الاستضافة. لا تعالج الفشل بتعطيل TLS. إن نجح تسجيل الدخول وفشل عرض المجلد، راجع دعم Passive FTPS ومنافذه في الاستضافة.

## ما يُبنى وما يُرفع

يستخدم البناء Node.js 24 وpnpm 11.25.0 و`pnpm install --frozen-lockfile` ثم `pnpm build` و`pnpm verify:build`. يبقى إعداد Vite الحالي `base: './'`. النتيجة الوحيدة المرشحة للرفع هي **محتويات `dist/`**، لا مجلد المشروع ولا مجلد `dist` كطبقة إضافية على الخادم.

يفحص `scripts/ftps-deploy.py validate` قائمة صريحة من ملفات الواجهة: `assets/` و`index.html` وأيقونات الموقع وملف manifest وصفحات السياسات والدعم والصيانة و404 و`offline-assets.json` و`sw.js`. يرفض الملفات الزائدة والمسارات غير الآمنة والروابط الرمزية وعدم اتساق بيان الملفات. لا تدخل المصادر أو الأسرار أو `node_modules` أو `content/` أو `dist-engineering/` أو تقارير الاختبار في الرفع. فحص البناء القائم يمنع تسرب قدرات التدريب الصناعي والمحتوى المحجور.

## مسارا GitHub Actions

### Verify build and read-only FTPS

`verify-ftps.yml` يبني ويفحص عند تعديل ملفات إعداد FTPS في فرع المستودع، وعلى Pull Request، ويمكن تشغيله يدويًا بعد الدمج. بعد نجاح البناء، تختبر دفعة موثوقة إلى المستودع أو تشغيل يدوي الاتصال باستخدام الأسرار. مهمة Pull Request لا تحصل على أسرار FTP ولا تختبر الاتصال. لا يحتوي هذا المسار على أمر نشر؛ أوامر الاختبار لا ترفع ملفًا ولا تنشئ مجلدًا ولا تحذف شيئًا. الغرض من تشغيله على فرع هذا الطلب هو اختبار الأسرار والاتصال قبل الدمج دون تغيير الإنتاج.

### Manual FTPS deployment

`deploy-ftps.yml` لا يحتوي على أي trigger آلي للنشر. يظهر التشغيل اليدوي الاعتيادي بعد دمجه في الفرع الافتراضي بموافقة المالكة:

1. شغّل `Manual FTPS deployment` مع `operation=check` أولًا؛ هذا هو الخيار الافتراضي، ويجري بناءً وفحص اتصال فقط.
2. قبل أول نشر: احسم تعارض النطاق والسياسات الموضح أدناه، وتحقق من إعدادات HTTPS والاستضافة، وأنشئ نسخة احتياطية على الاستضافة ونسخة من الإصدار السابق. أكمل اعتماد بوابات الإصدار العلمية والهندسية في عمل مستقل؛ نجاح البناء ليس بديلًا عنها.
3. اضبط مراجعين إلزاميين لبيئة GitHub المسماة `production-ftps` وقيّدها إلى `main` إذا كانت خطة المستودع تدعم ذلك. مجرد وجود اسم البيئة في YAML لا يعني أن الحماية مفعلة. صلاحية التكامل لا تثبت وجود هذه الحماية؛ يجب التحقق منها في إعدادات GitHub. لا تنقل الأسرار من مستوى المستودع دون تحديث مسار الفحص أيضًا.
4. بعد موافقة المالكة على الإصدار المحدد، اختر `main` و`operation=deploy` وأدخل حرفيًا `DEPLOY mulazama.com`. أي فرع آخر أو تأكيد مختلف يُرفض قبل الاتصال. يُبنى SHA الذي اختاره GitHub لذلك التشغيل ويُنقل artifact من التشغيل نفسه إلى مهمة النشر.
5. يوقف `verify-release.mjs` النشر إذا كانت البوابات محجوبة (exit 2) أو فاشلة. بعد انتظار مراجعة البيئة، يُفحص أقرب انتهاء للاعتمادات المتحقق منها مرة أخرى مع اشتراط بقاء 15 دقيقة على الأقل، تغطي المهلة القصوى لمهمة الرفع. **في حالة المشروع الحالية سيظل النشر محجوبًا حتى مع التأكيد اليدوي**. لا تعدّل السكربت أو تتجاهل المخرج لتجاوز الاعتماد.
6. بعد نجاح البوابات وفحص الاتصال ومراجعة البيئة إن كانت مفعلة، تُرفع الملفات المعتمدة فقط. تُرفع الأصول أولًا، ثم ملفات الواجهة، ثم `index.html` و`sw.js` أخيرًا. مهام النشر متسلسلة ولا تُلغى تلقائيًا أثناء الرفع.

الأوامر المحلية للمراجعة دون نشر:

```sh
python3 scripts/tests/ftps-deploy.test.py
pnpm build
pnpm verify:build
python3 scripts/ftps-deploy.py validate
# يتطلب الأسرار في بيئة العملية؛ لا تكتب قيمها في الأوامر أو المحادثة:
python3 scripts/ftps-deploy.py check
```

## سلامة الملفات والبيانات والتراجع

أداة الرفع لا تنفذ `DELE` أو `RMD` أو مزامنة حذف، ولا تمس ملفات غير موجودة ضمن قائمة البناء. تبقى `.htaccess` وملفات الخادم والرفع ونسخ البيانات القديمة خارج نطاقها. الملفات ذات الأسماء المطابقة لملفات البناء تُستبدل **فقط عند نشر معتمد**؛ لا يعني عدم الحذف عدم الاستبدال. تبقى الأصول القديمة ذات الأسماء المشتقة من المحتوى لدعم العملاء الذين لم يحدثوا بعد؛ تنظيفها عمل منفصل بموافقة صريحة.

FTPS لا يوفر تبديل إصدار كاملًا ذريًا: فشل الرفع قد يترك ملفات من إصدارين رغم ترتيب الملفات لتقليل الخطر. عند الفشل، راجع السجل قبل إعادة المحاولة؛ لا تفعّل إعادة نشر آلية عمياء. يتطلب التراجع artifact سابقًا معتمدًا أو نسخة الاستضافة الاحتياطية، ومراجعة توافقه مع بيانات العملاء. لا تستخدم مجلد المصادر كنسخة نشر، ولا تحذف بيانات IndexedDB أو تغيّر إصدارها أثناء التراجع. هذا الإعداد لا يغير محرك FSRS أو قارئ الأحداث أو مخطط التخزين أو تفعيل القرآن.

## مسائل قائمة قبل الإطلاق

- تشير `deployment/environments06l4.json` وصفحات `public/privacy.html` و`public/support.html` و`public/terms.html` إلى `mulazama.sa`، بينما الوجهة المطلوبة هنا `mulazama.com`. لم تُعدّل السياسات أو عناوين الاتصال في مهمة البنية التحتية هذه، ويجب اعتماد التصحيح والتحقق من الاختبارات المرتبطة به قبل الإطلاق.
- `deployment/headers.example` مثال فقط؛ هذا الرفع لا يثبت إعداد HTTPS أو أنواع MIME أو Cache-Control أو رؤوس الأمان أو استجابات 404/503 في الاستضافة. يجب التحقق منها على البيئة المقصودة بصورة مستقلة.
- نتائج فحص الاتصال الفعلية وأرقام التشغيل وحالة الاختبارات تُسجّل في وصف Pull Request؛ لا يُعد مجرد وجود ملفات YAML دليل نجاح اتصال.
- يمكن لاحقًا تحويل النشر إلى trigger على `push` إلى `main` في Pull Request مستقل بموافقة المالكة، مع الإبقاء على بوابات الاعتماد ومراجعة البيئة وتسلسل الرفع والتحقق من artifact ومنع الحذف. لا يكفي إضافة trigger وحده: يجب تعديل شروط النشر والمدخلات اليدوية عمدًا ومراجعتها. لم يُفعّل ذلك هنا.
